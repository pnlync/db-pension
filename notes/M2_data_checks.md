# M2 数据检查与成员对账

> 成员数据是合成的。

## 这一步做了什么

管理方交来的 2025-12-31 原始数据不能直接拿来估值。这一步做四件事：
1. 逐条按规则检查。
2. 把每个问题连同处理方式写进 `outputs/data_issues.csv`。
3. 只用有依据的来源修正：去年核对过的数据，以及管理方的变动报告。
4. 核对"期初 + 转入 − 转出 = 期末"。

原则：**不静默修改**。审计师会逐条问每一处改动的依据。

## 检查规则（顺序固定）

**第一轮：身份和日期。** 年龄类规则依赖正确的出生日期，所以这一轮先做。

| 规则 | 检查内容 | 处理 |
|---|---|---|
| uniqueness | member_id 唯一 | 完全相同的重复行删掉一条；内容不同则向管理方查询 |
| traceability | 能追溯到期初数据 | 剔除，不参与估值，并向管理方查询 |
| completeness | 各状态的必填字段齐全 | 出生日期从期初数据取回；其他字段向管理方查询 |
| date_order | 出生 < 入职 < 离职或退休 ≤ 估值日 | 用期初数据里的出生日期修正 |

**第二轮：取值和状态。**

| 规则 | 检查内容 | 处理 |
|---|---|---|
| age_range | 年龄 18–110 岁 | 向管理方查询 |
| service_vs_age | 服务年数 ≤ 年龄 − 18 | 在职成员按入职日期重新计算 |
| salary_range | 工资 €10k–€500k | 用变动报告里 1 月加薪后的工资替换 |
| active_no_exit_date | 在职成员没有离职或退休日期 | 变动报告里没有退出记录，就删掉这个日期 |
| deferred_no_salary | 递延成员没有工资 | 清空工资 |
| pension_positive | 递延和退休成员的年金 > 0 | 用变动报告里 2025 年的年金替换 |

清洗后再把所有规则跑一遍，必须零问题，否则程序直接报错。

## 理解检查（自测）

1. **每类错误怎么处理？为什么要留记录？** 见上面两张规则表。留记录是因为估值结果要经得起审计：每一处改动都要说得出依据，而且下一年能复现。
2. **为什么出生日期的检查要先做？** 年龄、"服务 ≤ 年龄 − 18"都依赖出生日期。出生日期错了，后面的规则会连带报出假问题。
3. **来历不明的记录为什么不直接当作新成员保留？** 计划 2012 年起不收新成员，期初数据里没有这个人，变动报告里也没有。这是数据错误，保留会凭空增加负债。

## 面试要点

- "Checks run in a fixed order, identity and dates first, and the cleaned file is re-checked to zero issues."
- "Each correction cites its source (last year's data or the movement report); anything without a source is queried, not guessed."
